# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

TYPO3 extension **`twtgroup/headliner`** (TER key `headliner`, PHP namespace `Twtgroup\Headliner\`). The
extension is at the start: scaffolding (DDEV, CI, release workflow, tooling) is in place, the extension code is not.
Release notes: `CHANGELOG.md` (keep it updated with every user-visible change).

## How to work in this repo

Work **TDD**: write-failing-test → run (verify FAIL) → minimal implementation → run (verify PASS) →
commit. Don't batch unrelated changes or skip the failing-test step; commit at logical boundaries.

## Commands

Dependencies install into `.Build/` (a Composer `vendor-dir`, not the default `vendor/`):

```bash
composer update                                          # installs into .Build/
.Build/bin/phpunit -c Build/phpunit/UnitTests.xml        # all unit tests (pure PHP, fast)
.Build/bin/phpunit -c Build/phpunit/FunctionalTests.xml  # functional tests (boot TYPO3 + DB)
```

Dev tooling pinned in `require-dev`: `phpstan/phpstan ^2.1`, `friendsofphp/php-cs-fixer ^3.51`.

### DDEV testbed

The committed `.ddev/` config (nginx-fpm, PHP 8.3, MariaDB) provides a clickable sandbox. `ddev start` installs the
Composer dependencies and builds a ready-to-use TYPO3 on the first start (post-start hook; skipped once
`.Build/bin/typo3` and `config/system/settings.php` exist). Custom commands wrap the workflows:

```bash
ddev setup              # composer install into .Build/
ddev demo               # (re)build the demo at https://headliner.ddev.site/ (.Build/)
ddev test [unit|functional|all]   # PHPUnit suites
ddev lint               # PHPStan + php-cs-fixer (dry-run); `ddev cgl-fix` auto-fixes
ddev scan-extension [--strict]    # TYPO3 Extension Scanner (Install Tool "Scan Extension Files") on CLI
```

Backend login: `https://headliner.ddev.site/typo3/`, user `admin`, password `Password.1` (local demo only; the
default lives in `Build/Scripts/setup-demo-instance.sh`, `ADMIN_PASS` overrides it). The instance (`config/`, `var/`,
`.Build/`, database) is git-ignored and fully regenerated by that script.

## Test layering (important for speed)

Tests split into two suites by what they need to boot:
- **`Tests/Unit/`** — pure PHPUnit `TestCase`, no TYPO3 bootstrap. Keep framework-free logic here so
  it runs fast.
- **`Tests/Functional/`** — `typo3/testing-framework`, boots TYPO3 + DB. Used for anything touching
  FAL, middlewares, TCA, or ViewHelpers. They must restore request-related globals: the testing framework does not
  reset `$GLOBALS['TYPO3_REQUEST']` / `BE_USER`, so save them in `setUp()` and restore them in `tearDown()`.

## Project decisions

- Version lives in `ext_emconf.php` AND `composer.json` (`extra.typo3/cms.version`, needed to avoid the TYPO3 14.3
  `ext_emconf.php` deprecation) - keep both in sync on release; `ext_emconf.php` stays for TER.
- Releases: tag `vX.Y.Z` on a green `main` commit; `.github/workflows/release.yml` creates the GitHub release from the
  CHANGELOG section (`Build/Scripts/release-notes.sh`) after checking the tag against `composer.json`/`ext_emconf.php`.
  The same workflow has a `ter` job (Tailor `ter:publish`, comment = `release-notes.sh --plain`) that is a no-op until the
  repo secret `TYPO3_API_TOKEN` exists and skips versions already in TER. On a tag push it first calls `ci.yml`
  (`workflow_call`) on the tagged commit and publishes only if it is green; a manual run for an existing tag skips CI.
- Extension Scanner: `Build/Scripts/extension-scan.php` must report no *strong* matches. Silence false positives (a
  method name that only looks like a core one) with a `// @extensionScannerIgnoreLine` comment above the line and say why.
- Prefer TCA-derived DB columns over `ext_tables.sql` (the core derives columns from TCA via
  `DefaultTcaSchema`); use an auto-creating type (`check`, `input`, `number`, `text`, `datetime` - NOT `passthrough`).

Supported: **PHP 8.3+ / TYPO3 14.3** (`composer.json`, `ext_emconf.php`).
