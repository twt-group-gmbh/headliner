# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

TYPO3 extension **`twtgroup/headliner`** (TER key `headliner`, PHP namespace `Twtgroup\Headliner\`). The
extension is at the start: scaffolding (DDEV, CI, release workflow, tooling) is in place, the extension code is not.
Release notes: `CHANGELOG.md` (keep it updated with every user-visible change).

## How to work in this repo

Work **TDD**: write-failing-test → run (verify FAIL) → minimal implementation → run (verify PASS) →
commit. Don't batch unrelated changes or skip the failing-test step; commit at logical boundaries.

## Commands

Dependencies install into `.Build/` (a Composer `vendor-dir`, not the default `vendor/`):

```bash
composer update                                          # installs into .Build/
.Build/bin/phpunit -c Build/phpunit/UnitTests.xml        # all unit tests (pure PHP, fast)
.Build/bin/phpunit -c Build/phpunit/FunctionalTests.xml  # functional tests (boot TYPO3 + DB)
```

Dev tooling pinned in `require-dev`: `phpstan/phpstan ^2.1`, `friendsofphp/php-cs-fixer ^3.51`.

### DDEV testbed

The committed `.ddev/` config (nginx-fpm, PHP 8.3, MariaDB) provides a clickable sandbox. `ddev start` installs the
Composer dependencies and builds a ready-to-use TYPO3 on the first start (post-start hook; skipped once
`.Build/bin/typo3` and `config/system/settings.php` exist). Custom commands wrap the workflows:

```bash
ddev setup              # composer install into .Build/
ddev demo               # (re)build the demo at https://headliner.ddev.site/ (.Build/)
ddev test [unit|functional|all]   # PHPUnit suites
ddev lint               # PHPStan + php-cs-fixer (dry-run) + XLIFF lint (`Build/Scripts/xlf-lint.php`: valid XLIFF) + prettier
                        # (formatting of the *.xlf); `ddev cgl-fix` auto-fixes PHP,
                        # `ddev npm run lint:xlf-fix` fixes the XLIFF formatting
ddev scan-extension [--strict]    # TYPO3 Extension Scanner (Install Tool "Scan Extension Files") on CLI
ddev docs               # render Documentation/ with the TYPO3 docs toolchain (Docker); fix every warning
```

The demo has subpages with different heading structures (clean, two H1, no H1, div headers, RTE headings, no headings);
see `Build/Scripts/setup-demo-instance.sh`. It also has a second site language, German (`/de/`), with translated
pages (`/de/ueber-uns`, `/de/produkte`, `/de/kontakt`) and content elements. `ddev demo` resets the database, so an open
backend session is gone afterwards: log in again.

Backend login: `https://headliner.ddev.site/typo3/`, user `admin`, password `Password.1` (local demo only; the
default lives in `Build/Scripts/setup-demo-instance.sh`, `ADMIN_PASS` overrides it). The instance (`config/`, `var/`,
`.Build/`, database) is git-ignored and fully regenerated by that script.

## Test layering (important for speed)

Tests split into two suites by what they need to boot:
- **`Tests/Unit/`** — pure PHPUnit `TestCase`, no TYPO3 bootstrap. Keep framework-free logic here so
  it runs fast.
- **`Tests/Functional/`** — `typo3/testing-framework`, boots TYPO3 + DB. Used for anything touching
  FAL, middlewares, TCA, or ViewHelpers. They must restore request-related globals: the testing framework does not
  reset `$GLOBALS['TYPO3_REQUEST']` / `BE_USER`, so save them in `setUp()` and restore them in `tearDown()`.
  The frontend tests extend `AbstractFrontendTestCase`: a site with the site sets (written with the core's `SiteWriter`)
  and a few headers, rendered through the real frontend application (`executeFrontendSubRequest()`); mark the request
  with `InspectRequest::ATTRIBUTE` to get the marks of the page module. The testing framework's own frontend middleware
  needs the request attribute `typo3.testing.context`, which only its own way of requesting sets, so
  `TestingContextRequestHandler` adds it when a test calls the real `PageHtmlFetcher`.

## Project decisions

- No `ext_emconf.php` (deprecated in TYPO3 14): the version lives only in `composer.json` (`extra.typo3/cms.version`).
- Releases: tag `vX.Y.Z` on a green `main` commit; `.github/workflows/release.yml` creates the GitHub release from the
  CHANGELOG section (`Build/Scripts/release-notes.sh`) after checking the tag against `composer.json`.
  The same workflow has a `ter` job (Tailor `ter:publish`, comment = `release-notes.sh --plain`) that is a no-op until the
  repo secret `TYPO3_API_TOKEN` exists and skips versions already in TER. On a tag push it first calls `ci.yml`
  (`workflow_call`) on the tagged commit and publishes only if it is green; a manual run for an existing tag skips CI.
- Compatibility with `FriendsOfTYPO3/visual_editor` is a goal: always look at how it does things first. Texts stay
  `{record -> f:render.text(field: ...)}` (that is how it marks editable text), prefer core ViewHelpers and core
  mechanisms. `Resources/Private/Partials/Header/All.fluid.html` is a copy of the core partial: keep it in sync with
  `fluid_styled_content` and keep its `f:render.text` calls.
- The page module only holds a placeholder (`Placeholder.html`); `headlines.js` loads the box from the AJAX route
  `ajax_headliner_structure` (`StructureController` -> `StructureBox`, which does the checking and draws
  `Headlines.html`), also while it is collapsed, so the summary shows the problems. Lazy loading instead of a cache: the
  content is edited in the backend, so a cache would have to be invalidated by every change. The controller is a public
  service (the route gets it from the container) and checks the right to see the page. `returnUrl` of the edit links is
  the page module's URL, passed by the JavaScript (the AJAX request itself is not a place to return to).
- Which languages the box shows follows the page module, see `SelectedLanguages`: the layout view shows its "primary"
  language (the one translation if exactly one is selected, else the default language), the language comparison shows
  the default language plus the selected translations. `languages` in the module data alone is not enough: in the
  comparison it can be `[1]` while two columns are shown.
- Opening a content element from the page module box uses the core's `be:link.editRecord contextual="true"` (custom
  element `typo3-backend-contextual-record-edit-trigger`), so it slides in from the right like the core's own edit
  buttons. Do not build edit URLs by hand.
- The content of the page is what is checked: `HeadingExtractor::extract($html, $selector)` marks headings that are not in the
  elements of the site setting `headliner.contentSelector` (empty by default: the whole page) as `outside`; `HeadingValidator` skips their levels except h1 (an h1 outside counts for
  missing and multiple h1, even if it cannot be edited), the box shows them very pale (not if they have a problem). No match, an empty or an invalid selector: the whole page (never show nothing). `symfony/css-selector`
  (a requirement) turns the selector into XPath.
- Headings from the text of a content element (RTE) can have a tag select, but only with the site setting
  `headliner.editRteHeadings` (default off, it changes the editors' text), checked in the box and again in
  `RteHeadingEditor`. The heading is matched with its place in `bodytext` by `RteHeadings` (the n-th heading of the text,
  same level and text), the tag must be one of `heading.options` of the RTE configuration (`Richtext::getConfiguration()`),
  and the field is saved through the DataHandler (never by writing to the database). Nothing is changed if the heading is
  not found where the order says.
- What a backend user may do in the box is decided by `EditAccess`, with the rules of the page module's own edit buttons
  (`GridColumnItem::isEditable()`); the fields `header_tag` and `subheader_tag` are "exclude" fields, so they also need
  the field permission. Never show the select or the link on the basis of the markup alone.
- `PageHtmlFetcher` renders the frontend in the same PHP process (a sub-request through the core's `RequestHandler`),
  not over HTTP. The frontend middleware stack changes `BE_USER`, `TYPO3_REQUEST`, `LANG`, the Context aspects and the
  shared `PageRenderer`, so the fetcher puts them back (unit-tested); if you add state the sub-request touches, restore
  it there too. It marks the sub-request with the request attribute `headliner.inspect`. Only then `InspectRequest`
  (frontend middleware) disables the page cache for that request, and `headliner:headline` adds
  `data-headliner-edit="table:uid:field"`. The attribute exists only inside the PHP process, a request from outside
  cannot set it (no header, no secret). That markup must never be cached or shown to visitors.
  For such a request `InspectRequest` also includes hidden pages (not hidden content) in the visibility, so a page that is
  not published yet can be checked; it must run before `page-resolver`, where a hidden page is turned down.
  With the attribute `headliner.inspect.time` it also simulates that time (date aspect plus the globals `SIM_EXEC_TIME` and
  `SIM_ACCESS_TIME`, which the start/end time restrictions read), computed by `PublicationTime` from the root line. The
  fetcher puts those globals back.
  With `headliner.inspect.groups` (from `FrontendGroupAccess`) it renders the page as a member of the page's frontend user
  groups by replacing the aspect `frontend.user`, so it has to run after `typo3/cms-frontend/authentication`.
  With `headliner.inspect.workspace` (the workspace of the backend user) it replaces the aspect `workspace`, so the frontend
  overlays the versions. The marks then name the *live* uid: that is what the DataHandler wants in a workspace, it writes
  to the version. The page, translation and root line the listener computes with are the workspace versions
  (`getRecordWSOL`, `workspaceOL`, `BEgetRootLine(..., true)`). What the page module simulates is passed as one
  `Simulation` (time, groups, workspace).
- Extension Scanner: `Build/Scripts/extension-scan.php` must report no *strong* matches. Silence false positives (a
  method name that only looks like a core one) with a `// @extensionScannerIgnoreLine` comment above the line and say why.
- Prefer TCA-derived DB columns over `ext_tables.sql` (the core derives columns from TCA via
  `DefaultTcaSchema`); use an auto-creating type (`check`, `input`, `number`, `text`, `datetime` - NOT `passthrough`).

Supported: **PHP 8.3+ / TYPO3 14.3** (`composer.json`).
